## Video: JSON и сцены

**Формат JSON:** построчные объекты (`scene_id`, `text`, `start`/`end`/`video` с `prompt`), не обязательно один массив.

**Страница job** (`job.html`, `app.py`, `style.css`):
- Секция **«JSON-код сцен»** — сворачиваемая карточка в стиле **«Озвучка ElevenLabs»**
- **Источник текста** — textarea `#json_input`, Scenes, ✎, копировать, счётчики
- Настройки в одну строку: Aspect Ratio, Resolution, Image/Video Model, шаблон изображений
- Над **«Добавить сцены»** — разделитель (`tts-divider`) и вложенная карточка **«Тайминги Scenes»** (как «Тайминги Eleven»): 50/50 «данные / проверка», ↻, Result, Pending
- Свёрнутая шапка: `Scenes | Сцен N | Тайминги Result | Проверка NO/OK`
- Оверлей **«Редактировать»** после добавления сцен; в свёрнутом виде компактная строка и заголовок **под** оверлеем (файлы 57–58)
- Сетка сцен: сворачивание по одной, `scene_001 — 3.42 с`, бейджи Start/End/Video, поллинг Kie (720p/1080p)

**Связь с ReWrite:** Scene Writer подставляет JSON в Video; озвучка (Eleven, Whisper, тайминги, проверки слов) на той же job-странице.

## Как работает проверка

Для каждого блока Structure Splitter сравнивается:

1. **Исходный текст блока** (`text` из Structure Splitter, у блока 4 — **1168** символов).
2. **Склейка полей `text` всех сцен** этого блока (7 сцен, через перевод строки), с нормализацией пробелов.

```1080:1091:/srv/json_video/app.py
    merged_scene_text = "\n".join(str(s.get("text") or "") for s in scenes)
    ok = _norm_ws(merged_scene_text) == _norm_ws(block_text)
```

**OK** — только если весь текст блока **без изменений** разбит на сцены: без перефраза, без пропусков, без лишнего. Это совпадает с промптом Scene Writer («не менять текст»).

`with_end: 0` на проверку **не влияет** — поле `end` в парсере не учитывается.

В Result попали **только первые ~509 символов** из 1168. Остальные **~659 символов** в сценах **отсутствуют**.

## Источник на экране сцен

На карточках (`22:35.47 → 22:42.54`, длительность в секундах) показывается поле **`audio_timing`** у каждой сцены в `job.json` — поля `start_ms`, `end_ms`, `badge` и т.д.

## Откуда появляется `audio_timing`

1. **Текст сцен** — из `job["scenes"][].text` (после «Добавить сцены» / parse JSON).

2. **Пословные тайминги** — из файла слов к последней озвучке в `data/job_audio/<job_id>/`:
   - **ElevenLabs** → `<имя_озвучки>.words.json` (после TTS с timestamps);
   - **Whisper** → `<имя_озвучки>.whisper.words.json` (локальный Whisper).

3. **Выравнивание** — функция `align_scenes_to_word_timings()` (`job_scene_audio_align.py`): сопоставляет текст каждой сцены со словами в JSON и выставляет границы `start_ms` / `end_ms`.

4. **Какой источник слов** — поле **`job["apply_timings_source"]`** (`elevenlabs` или `whisper`): то, что выбрано в блоке **«Тайминги Scenes»** (радиокнопки Eleven / Whisper). Если Whisper недоступен, при монтаже подставляется ElevenLabs.

Тот же пересчёт делается при:
- **«Добавить сцены»** (если есть words.json);
- кнопке **↻** в «Тайминги Scenes» (`/job/.../scenes/apply-tts-timings`).

## Что делает именно «Собрать ассеты» (монтаж)

1. Берётся **последний MP3** из `data/job_audio/<job_id>/` (у вас `20260520_173802_157839985.mp3`).

Для вашего **«Рендерить MP4»** (Remotion `JobMontage` + ffmpeg) картина такая:

## В основном — **процессор (CPU)**

Большую часть времени ест именно CPU:

1. **Отрисовка кадров** — headless Chromium рисует каждый кадр (у вас десятки тысяч: 40 875 при ~22 мин @ 30 fps): зум, картинки, fade.
2. **Сборка / композ** — Node, bundler.
3. **Кодирование MP4** — ffmpeg (x264 и т.п.) тоже грузит CPU.

Поэтому в логе «1h 46m remaining» и растёт `Rendered N/M` — это почти всегда скорость **ядер**, а не «мало RAM».

## Оперативка тоже важна, но чаще как потолок

RAM нужна на:

- сам **Chrome/Chromium** под Remotion;
- **буферы кадров** и композиция;
- **медиа** (328 сцен — картинки/видео в `media/`).

На сервере сейчас **~8 ГБ RAM, 4 ядра, без swap**. Пока рендер идёт, ещё работают **json-video** (5000) и **Remotion Studio** (3000) — они тоже едят память. Если RAM кончается — процесс могут **убить (OOM)**, тогда в UI будет похоже на обрыв («Failed to fetch»), хотя причина — память, а не сеть.

## Диск — второстепенно

Чтение **сотен файлов** из `data/job_remotion/.../media/` и запись **out.mp4** — обычно не главный тормоз, если диск не перегружен.

## Практически для вашего проекта

| Ресурс | Роль |
|--------|------|
| **CPU** | Главный лимит скорости (~2+ ч на полный ролик на 4 ядрах — нормально). |
| **RAM** | Держит Chrome + кадры; при 8 ГБ лучше не гонять параллельно много тяжёлых задач. |
| **Сеть** | Только опрос статуса в браузере; на сам рендер почти не влияет. |

**Совет:** на время длинного рендера не запускайте второй полный рендер и по возможности закройте лишние вкладки Studio; мониторинг: `htop` — если все ядра ~100% и мало free RAM, упираетесь в CPU/RAM соответственно.

Ускорение в основном: **больше ядер**, меньше длительность/разрешение/fps, или рендер кусками — не «добавить RAM» одной линейкой.
