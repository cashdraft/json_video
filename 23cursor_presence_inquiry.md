### В чём была причина

В `runBulkGeneration` вызывалось **`startGenerationForButton(..., { bulk: true })` без `await`**. ### Что сделано

1. **`await startGenerationForButton(...)`** в цикле пакета — пока идёт хотя бы одна задача, **`bulkRunActive` остаётся true**, «Остановить» активна.
2. **`try / finally`** — `bulkRunActive` сбрасывается только после выхода из цикла (в том числе при остановке).
3. В начале пакета **`bulkStartedTaskIds.clear()`**, чтобы не слать cancel по старым id.
4. По **«Остановить»**: все известные `task_id` попадают в **`canceledTasks`**, чтобы **`pollTask`** вышел из цикла; плюс по-прежнему вызывается **`/generate/cancel`** на сервере.
5. После выхода из опроса по отмене слот показывает **Canceled**; если остановка наступила сразу после `start` — короткое сообщение в журнале.

1. **POST** `/job/<id>/download-all/start` — запускает сборку ZIP в **фоновом потоке**, сразу отдаёт `task_id` и план (сколько шагов, сколько картинок/видео/озвучки).
2. **GET** `/job/<id>/download-all/status?task_id=…` — JSON с прогрессом: шаги, счётчики файлов, байты по категориям, текущая операция, при скачивании по URL — **сколько уже скачано байт** этого файла.
3. **GET** `/job/<id>/download-all/file?task_id=…` — отдаёт готовый ZIP (после ответа временный файл удаляется).

Старый **GET** `/job/<id>/download-all` без изменений по смыслу (одним запросом, без прогресса).

### Интерфейс
- Полоса прогресса по шагам (`steps_done / total_steps`), во время загрузки с URL слегка «подползает» вперёд.
- Строка под полосой: шаги, число файлов в архиве, план по картинкам/видео/озвучке.
- Блок детализации: объёмы изображений / видео / озвучки (до сжатия ZIP), при активной загрузке — **объём текущего URL**, в конце — **размер готового ZIP**.
- Если сервер без новых маршрутов (**404** на `start`), остаётся прежний режим одним **GET** `download-all`.

### Код
- `app.py`: план шагов `_archive_plan_steps`, общая сборка `_run_archive_into_zipfile`, фоновый воркер, хранение задач в памяти (один процесс `run_server.py` — этого достаточно).
- `_fetch_url_bytes_capped(..., on_progress=…)` — обновление байт во время стрима.
- `job.html` + `style.css` — модалка, опрос ~450 мс, стили прогресс-бара.

Исправление внесено только в **фронтенд** (`job.html`), перезапуск сервера не нужен.

### В чём была ошибка
Опрос шёл через **`setInterval(() => { void tick(); }, 450)`** — следующий **`tick()`** запускался **не дожидаясь** окончания предыдущего. Параллельно могли идти:

1. один поток уже получил `done`, начал **`/download-all/file`** и после ответа сервер **удалил задачу** из памяти;
2. второй поток всё ещё вызывал **`/download-all/status`** → **`unknown_task` → 404**;
3. в `pollOnce` это превращалось в **`throw new Error('status 404')`** и показывалось «Ошибка опроса статуса», хотя архив уже был собран и частично даже отображён в UI.

### Что сделано
Вместо интервала — **цепочка `setTimeout` с `await tick()`**: следующий опрос ставится в очередь **только после** полного завершения предыдущего `tick()` (включая скачивание ZIP). Параллельных опросов/двойного `finalize` больше не будет.

`stopDownloadAllPoll` теперь сбрасывает и **`clearTimeout`**, и **`clearInterval`** (на случай старого кода в кэше).

### Почему «зависало»
После строки **«Скачивание готового ZIP…»** шёл `fetch` и затем **`await r.blob()`** на весь архив (~200 МБ). Пока весь ответ не прочитан в память, промис не завершается: вкладка может **долго не реагировать**, без прогресса в модалке (прогресс есть только в панели загрузок, если вообще дошло).

### Что сделано
Вместо `fetch` + `blob` + `createObjectURL` используется **обычная ссылка**: программный клик по `<a href="…/download-all/file?task_id=…" download="…">`. Браузер сам качает файл **как обычную загрузку** (меньше памяти, виден прогресс в загрузках).

Модалка сразу переходит в **«Готово»** с текстом, что загрузка идёт в панели загрузок и большой архив может идти несколько минут.
