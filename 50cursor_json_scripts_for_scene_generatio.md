## Почему так у Eleven

Озвучка в **одном чанке** (`total_chunks: 1`), но alignment ElevenLabs **ломается** на большом куске текста:

- **89 слов** с одним и тем же `start_ms` (70 847) — тайминги «схлопнуты».
- Ещё кластеры: 47 слов @ 68 845, 30 @ 65 647 и т.д.
- В конце: «быстро», «готовите.», «Оба», «накормят,» — все с `start_ms = end_ms = 88 518`.
- После этого только «стоимость» и «разная.» (последняя растянута на ~17 с: 95 798–112 761).

В MP3 **после 112 с речь есть** — Whisper там находит **99 слов** (в т.ч. тот же финал «стоимость» / «разная.» около 164 с). Тишина только в самом хвосте (~161–164 с).

Итого: это не ошибка UI, а **неполный/битый character-alignment ElevenLabs** относительно полного MP3. Поле `total_duration_ms` берётся из ffprobe по MP3 (верно), а массив `words` — из API и обрывается раньше.

### Как устроено у нас

1. **Один HTTP-запрос на чанк** — эндпоинт ElevenLabs  
   `POST /v1/text-to-speech/{voice_id}/with-timestamps`  
   (см. `text_to_speech_with_timestamps` в `elevenlabs_client.py`).

2. **В одном ответе** приходит JSON с двумя частями:
   - `audio_base64` — MP3 озвучки;
   - `alignment` — посимвольные тайминги (`characters`, `character_start_times_seconds`, `character_end_times_seconds`).

3. **На нашем сервере** (в стриме `/job/.../elevenlabs/tts/stream`):
   - MP3 декодируется и сохраняется;
   - из `alignment` локально собирается массив слов (`chars_to_words_ms`);
   - рядом с MP3 пишется **`.words.json`** — это уже **наш** файл, не отдельная загрузка в Eleven.

4. **Если текст длинный** — несколько таких же запросов `with-timestamps` (по чанкам до лимита символов), потом **склейка MP3** через ffmpeg и склейка слов со сдвигом по длительности каждого куска (ffprobe).

### Итого

| | |
|---|---|
| Доп. запрос в Eleven за тайминги? | **Нет** |
| Озвучка + alignment | **В одном ответе** `with-timestamps` |
| `.words.json` в UI | Собираем **мы** из alignment и отдаём как файл с диска |

Whisper — это уже **отдельный** локальный прогон по готовому MP3 (`POST /whisper/words`), к Eleven он не относится.

## 1. Уменьшить чанки (даже если текст &lt; 5000)

**Суть:** не ждать лимита 5000, а резать, например, на 800–1500 символов по предложениям (та же `split_tts_text_into_chunks`, но с меньшим `max_chars`).

**Плюсы:**
- Меньше текста на один вызов `with-timestamps` — гипотеза: модель реже «схлопывает» alignment на длинном куске.

**Минусы:**
- Больше запросов → время, стоимость, риск микро-скачка на стыках голоса.

## 2. «Отдельно отправлять» — что реально возможно

| Вариант | Что это | Имеет смысл? |
|--------|---------|----------------|
| **Отдельный запрос только за словами** | У Eleven в вашем коде один endpoint: `with-timestamps` → сразу audio + alignment | **Нет** отдельного «только тайминги» в текущей интеграции |
| **Обычный TTS без timestamps + Whisper** | MP3 из `/text-to-speech`, слова из локального Whisper | **Да**, надёжнее по длине; дороже по времени, другой источник |
| **Несколько `with-timestamps`** | Уже так для текста &gt; лимита | **Да**, это и есть «отдельно по кускам» — не отдельный продукт, а несколько полных запросов |

Отдельно **гнать MP3 обратно в Eleven за alignment** в стандартном API нет — это уже STT (у вас Whisper).

## 3. Пост-проверка и автоматика (без смены API)

После каждого чанка (и в конце):

- `last_word.end_ms` vs `ffprobe` длительности чанка / всего файла;
- доля слов с `end_ms - start_ms <= 0` или с одинаковым `start_ms` подряд.

Если разрыв &gt; N секунд (у вас ~52 с):

- **ошибка / предупреждение** в UI («Eleven-тайминги не доходят до конца аудио»);
- **авто-retry** этого же куска меньшим размером или второй попыткой;
- не сохранять «зелёный» статус для сцен, если тайминги явно битые.

Сейчас жёсткий fail есть только при **массовом** коллапсе в начале (`chars_to_words_ms` ≥60% нулевой длительности) — **хвост** с частичным коллапсом может пройти.

**Cursor**

Да — **по умолчанию режем по предложениям**, не «кусок текста на 841 символ».

Цепочка такая:

1. **`sentences_split_by_dot`** — текст делится по **точке** `.`; каждый фрагмент снова с точкой, между предложениями при склейке добавляется ведущий пробел (чтобы не было `слово.Следующее`).
2. **`pack_sentences_into_chunks`** — предложения **склеиваются в чанк**, пока сумма ≤ лимита. Граница чанка — **между предложениями**, не посередине фразы.
3. **Жёсткая обрезка** `s[i : i + max_chars]` — только если **одно предложение длиннее лимита** (редко, но возможно).

То есть для обычного сценария с точками у вас 3–4 чанка из **целых предложений**, а не из произвольных 841 символов.

### Ограничения (чтобы не было сюрпризов)

| Ситуация | Что будет |
|----------|-----------|
| Нет точек в тексте | Весь текст = **одно «предложение»** → может резаться только по символам |
| Очень длинное предложение без точек | Режется **по символам** внутри него |
| `! ? …` | **Не** считаются границами — только `.` |
| Абзацы / переносы строк | Сами по себе **не** режут; только если внутри есть `.` |

## Goal

## Inputs

| Field | Source |
|--------|--------|
| `words[]` | `.words.json` |
| `total_duration_ms` | JSON (from ffprobe merged MP3) |
| Optional: real MP3 duration | ffprobe again if you want a cross-check |
| `total_chunks`, `chunk_limit` | metadata (informational only) |

- `clean[]` — words after SSML exclusion  
- `lastEnd = max(clean[i].end_ms)`  
- `firstStart = min(clean[i].start_ms)`  
- `mp3Ms = total_duration_ms`

## Check 1 — Coverage vs MP3 length (tail gap)

**Idea:** speech timings must reach almost the end of the file. This was the main failure mode before (MP3 ~2:49, Eleven words ~1:52).

```
tailGapMs = mp3Ms - lastEnd
```

| Result | Condition (starting thresholds) |
|--------|-------------------------------|
| **Fail** | `tailGapMs > 5000` (5 s of “silent” tail without words) |
| **Warn** | `2000 < tailGapMs ≤ 5000` |
| **Pass** | `tailGapMs ≤ 2000` |

Optional **head gap**:

```
headGapMs = firstStart
```

Fail if `headGapMs > 2000` (words start too late — rare).

**NO message example:**  
«Хвост: последнее слово заканчивается на 1:52, MP3 — 2:56 (разрыв 64 с).»

For your latest file (`20260517_111614`, 4 chunks): gap **39 ms** → **pass**.

## Check 2 — Zero-duration words

**Idea:** a normal word must have `end_ms > start_ms`.  
If `start_ms === end_ms`, it does not occupy time on the axis and breaks scene alignment.

For each `w` in `clean[]`:

```
durationMs = end_ms - start_ms
```

| Result | Condition |
|--------|-----------|
| **Fail** | any word with `durationMs ≤ 0` |
| **Fail (mass)** | share with `durationMs ≤ 0` ≥ 5% of `clean` |

**NO example:**  
«11 слов с нулевой длительностью (3,4%): «time="0.» @ 9480–9480 мс …».»

## Check 3 — “Pile-up” on one millisecond (your main mid-timeline concern)

Two related patterns.

### 3a. Adjacent words, same `start_ms`

```
sameStartPairs = count(i: clean[i].start_ms === clean[i-1].start_ms)
ratio = sameStartPairs / max(1, len(clean)-1)
```

| Result | Condition |
|--------|-----------|
| **Fail** | `ratio ≥ 0.15` (≥15% of pairs — collapsed alignment) |
| **Warn** | `0.05 ≤ ratio < 0.15` |
| **Pass** | `< 0.05` |

### 3b. Cluster: many words with one `start_ms`

Scan consecutive runs with the same `start_ms`:

```
cluster = maximal run where start_ms is equal
```

| Result | Condition |
|--------|-----------|
| **Fail** | any cluster length ≥ **8** words on one `start_ms` |
| **Warn** | cluster length 4–7 |
| **Pass** | max cluster ≤ 3 |

**NO example:**  
«Схлопывание: 89 слов с start_ms=82440 (фрагмент с 187-го по 275-е).»

This matches what you described: one word must not illegally sit on the same ms as another in a broken way — in practice Eleven expresses that as many tokens with **identical `start_ms`**, not as literal overlap.

---

## Check 4 — Overlap / time going backwards

**Idea:** along the speech timeline, the next word should not start clearly before the previous one ends (small tolerance for model noise).

For `i ≥ 1`:

```
overlapMs = clean[i-1].end_ms - clean[i].start_ms   // >0 = gap, <0 = overlap
```

| Result | Condition |
|--------|-----------|
| **Fail** | `overlapMs < -100` more than **3** times (start &gt;100 ms before previous end) |
| **Warn** | 1–3 such cases |
| **Pass** | none worse than −100 ms |

Also:

```
backwardEnd = clean[i].end_ms < clean[i-1].end_ms - 200
```

Fail if **backwardEnd** occurs ≥ 3 times (timeline “jumps back”).

---

## Check 5 — Coverage along the timeline (no long “dead zones”)

Divide MP3 into windows of **30 s** (or 15 s for short texts):

```
in each window [t, t+30s): count clean words with end_ms in window
```

| Result | Condition |
|--------|-----------|
| **Fail** | any window with **0** clean words while inside `[firstStart, lastEnd]` |
| **Warn** | word density in a window &lt; 30% of average |

Catches the case: beginning/end OK, middle ~30–60 s without usable timings.

|--------|-----------|
| **Fail** | `len(clean) < 20` |
| **Fail** | no `total_duration_ms` or `mp3Ms ≤ 0` |

## Схлопывание ms — OK

**Смысл:** таймлайн не «сломался» — слова не сидят десятками штук на **одной и той же миллисекунде** `start_ms`.

Это типичный баг Eleven, когда alignment «падает»: много токенов получают одинаковое начало, и по ним нельзя нормально резать сцены.

**Проверяется два условия (FAIL, если срабатывает хотя бы одно):**

| Условие | Порог | Пример FAIL |
|--------|--------|-------------|
| Соседние пары с одинаковым `start_ms` | ≥ **15%** всех пар подряд | каждое 7-е слово начинается в ту же ms, что и предыдущее |
| Кластер подряд | ≥ **8 слов** с одним `start_ms` | 89 слов @ 82440 мс |

**OK** значит: ни массового «один start на всех», ни большого кластера на одной метке нет. У вас тайминги идут слово за словом по времени — это нормально.

## Покрытие по 30 с — OK

**Смысл:** по всей длине речи нет **дыр** длиной ~30 секунд, где вообще нет ни одного чистого слова.

MP3 может быть ~3 минуты, слова в начале и в конце есть, а в середине alignment оборвался — сцены в этой зоне получат пустые или неверные тайминги. Эта проверка как раз ловит такие «мёртвые окна».

**Как считается:**

1. Берётся интервал от первого чистого слова до последнего.
2. Он режется окнами по **30 секунд** (0–30 с, 30–60 с, 60–90 с, …).
3. В каждом окне ищется хотя бы одно слово, у которого `end_ms` попадает в этот отрезок.
4. Если окно **пустое** → FAIL (в деталях: `окно 1:30–2:00`).

**OK** значит: на каждом 30-секундном куске шкалы есть хотя бы одно слово — тайминги «покрывают» дорожку по всей длине, без длинных провалов.

Обновляю разметку, логику построения дерева проверки и стили.


Готово для **Eleven** и **Whisper**:

1. **Убрана** строка «Проверка для сцен».
2. **OK / NO** теперь в первой строке рядом с **Проверка** (зелёный OK / красный NO).
3. **Дерево проверок:**
   - первая строка белая: `├─ Нулевая длина      FAIL — 2 слов`;
   - проблемные слова **ниже**, серым, **по одному на строку**: `«герой,» @ 49743–49743 мс`.

Обновите страницу (**Ctrl+F5**).
